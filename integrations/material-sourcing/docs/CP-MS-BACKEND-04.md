## Collaboration contract

The existing POST /api/materials transport accepts a dedicated collaborate command:
materialId, operationId, change. Supported changes are task.add, task.status,
task.remove, task.reorder, comment.add, comment.edit and comment.remove.
Material edits no longer write task or comment arrays or accept client-generated
activity messages. Server-generated material activity describes changed fields.
Star persistence remains in the existing material update path.

The server locks an operation identity and the active material row in a transaction.
READ COMMITTED collaboration operations read the latest committed child rows after
acquiring the lock. Independent additions and replies survive concurrent requests.
Task transitions/removal compare the expected status; reorder compares the expected
complete order. Comment edits/removals compare the previous edited_at timestamp.
Replies require a live comment within the same material; existing children survive
parent deletion through the existing tombstone mechanism. Failed commands roll back.
Ordinary material revisions remain independent of child-only modifications.
All audit events are generated by the server with the local-development actor and
database timestamps. Unknown historical authors are not presented as a known user.

Operation IDs are UUIDs. A server-generated activity event with a hashed operation
payload serves as the durable acknowledgement receipt. Replaying the identical operation
returns current data without a duplicate write/event; reuse for a different payload
is rejected. This is not a general distributed idempotency service.

## UI and recovery

Existing Details, Tasks and Activity layout is preserved. Database-mode tasks add
accessible up/down controls for persisted ordering. Task creation, new comment/reply,
and comment editing drafts are stored per material in browser-local storage; operation
identities survive refresh and drafts clear after acknowledgement. A failed or ambiguous
submission retains the input. For status/reorder/remove operations, refresh and review
the committed state before retrying if the acknowledgement is lost. Demo mode stays
browser-local and continues to use its existing interaction model.

## Boundaries

Actor identity is the existing local-development placeholder, not authenticated user
attribution. Mentions do not deliver notifications. Other sessions need refresh to
observe new activity; real-time subscriptions are later scope. Status checks compare
the expected state rather than a monotonically increasing per-task version, so a
task that cycles back to the same state is not distinguished from its earlier state.
Drafts are browser-local, not cross-device. The current READ COMMITTED collaboration
response uses the existing paginated snapshot retrieval; concurrent cross-material
snapshot consistency at large datasets is not certified. No Git repository is
configured. Manual user acceptance of the backend-enabled application remains open.
