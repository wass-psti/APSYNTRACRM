# CP-WS-02D/D — Trusted direct email provider integration and delivery integrity

## Scope and environment

Uses the existing WatchdogWorkspace project `jtlusodorfnyzgyuewkz` and existing private WS02D invitation contracts. No new users, roles, databases, projects, or permission systems. Live inspection on 2026-11-09 found that `private.ws02d_invitations` and `private.ws02d_issue` are absent, the deployed `ws02d-invite`/`ws02d-accept` Edge handlers are JWT-gated but intentionally return `unavailable`, and no `RESEND_API_KEY`, `WS02D_MAIL_SENDER`, or SMTP secret is configured. A GitHub Pages-only application must never receive mail provider keys or privileged database credentials.

## Implemented in this increment

- `server/ws02d-resend-provider.mjs` integrates Resend's official HTTPS email API without installing third-party SDK dependencies, explicitly default-off. Configuration must include a server-side API key and verified sender domain. Exact recipient email, bounded subject/body and UUID invitation ID are validated before any network request.
- Uses provider-supported `Idempotency-Key: apsyntra-ws02d-<invitation UUID>`, redirects denied, bounded request timeout, redacted provider errors and no automatic retry on ambiguous outcomes. Provider success yields only `{accepted: true, providerMessageId}`; never a claim that the message reached the inbox.
- `server/ws02d-trusted-mail-composition.mjs` composes the existing GoTrue/signed-issuer HTTP boundary with the provider; actual issuance, delivery audit and actor authorization must be independently supplied and enforced by a trusted backend, not browser input. Default-off integration invokes neither issuer nor provider.
- `server/ws02d-resend-webhook.mjs` verifies Resend/Svix HMAC signatures over raw payload bytes, rejects stale timestamps and malformed event correlation, and submits only an authenticated provider-message event to the injected durable state/audit adapter. No anonymous webhook is mounted on production; signature validation alone does not replace database-level event ID uniqueness.
- `sql/cp-ws02d-d-provider-event-ledger-candidate.sql` adds a private, RLS-enabled, default-deny durable provider event ledger with signed message-ID correlation and event-ID replay prevention. Its migration and synthetic verification are wired into the existing disposable PG17 workflow. It grants **no** browser or anonymous `EXECUTE`, never creates membership, and must not be installed without trusted backend signature enforcement.
- `server/ws02d-delivery-state.mjs` specifies a verified-only monotonic invitation lifecycle: pending -> provider submitted -> provider confirmed delivered -> recipient accepted, or failed/revoked/expired paths. A provider accepted response cannot transition directly to delivered. A provider webhook must be signature-verified by a trusted server before invoking the state reducer and applying a database transition.
- Focused tests use local in-memory fake provider receipts and check config denial, actor/audit association, idempotency, failure uncertainty, invalid envelopes, and state-transition denial. No real email is sent. The local suite also covers forged webhooks, expired signed payloads, provider failure and denied backend persistence.

## Activation and verification requirements

1. Provision or connect an *authorized, verified* mail sender/domain through an actual provider (e.g. Supabase's Resend integration), with server-only `RESEND_API_KEY` and `WS02D_MAIL_SENDER` secrets. Setup requires the provider account/domain holder; the test placeholder sender in this repository is not a verified sending domain.
2. Finish and install approved production private WS02D schema and restrictive grants after compliance with the existing recovery rehearsal policy. The local isolated PostgreSQL/Storage restore does not certify provider-hosted 24h RPO/RTO, and cannot be silently substituted for it.
3. Install the trusted signed-actor SQL integration that verifies live GoTrue user and session, workspace owner/delegated inviter, role ceilings, recipient email and one-time token. Bind issuance and receipt recording to the same signed actor and session, and preserve existing accounts and memberships.
4. Deploy the signed provider webhook and independent durable deduplication (signature + timestamp + event ID uniqueness), reconcile delivery failures and email-bounce statuses, and verify actual recipient inbox delivery before reporting `delivered`. An HTTP success from Resend is only `provider-submitted`.
5. Test new-user registration and activation using existing Supabase Auth, existing-user acceptance, mismatched email, foreign workspace, bootstrap restrictions, replay, expired/revoked tokens, concurrency, explicit role assignment through authorized User Role Management, and persistence across logout and refresh using approved nonproduction identities.
6. After all gates pass, activate the Edge handlers and frontend flags in a separately verified rollout. Do not bypass existing production recovery policy or privacy requirements, and never use the provided illustrative Gmail address as a live test recipient without confirming its intended ownership.

**Release disposition:** Implemented server provider and state integrity contracts; end-to-end production sending remains BLOCKED by external provider configuration and unfinished signed database activation. No production data or authorization was modified in this increment.
