# APSYNTRA CRM — Priority 5C: bounded signed startup and frame-stall diagnostics

## Evidence and problem scope

The user supplied the first five-second signed browser report on 2026-11-09: 591 frame intervals, P50 **8.3 ms**, P95 **9.2 ms**, 40.78% above the 8.33 ms budget, 0.68% above 16.67 ms; navigation TTFB **352.1 ms**, DOM ready **2287.4 ms**, load **2299.9 ms**. These are user-reported observations from one browser run; neither the display-refresh consistency nor the long tasks, backend, and module waterfall can be inferred from this report alone. The initial 2.3-second DOM-ready measurement does **not** establish a Supabase/authentication bottleneck.

## Verified new diagnostic boundary

- `frontend/performance-critical-path.js` records numeric phase durations of only three fixed, authorized startup phases: `session-restore` (awaiting signed authentication restoration), `workspace-authorization` (awaiting central workspace/context verification), and `authorized-route` (awaiting route and board initialization). The phase clock begins **after the JavaScript entry module is evaluated**; its `performance.now()` navigation-relative timestamp is retained as a numeric `entryFromNavigationMs`, and the final signed-route-ready timestamp as `signedReadyFromNavigationMs`. The difference between navigation and app entry can include HTML, import graph loading, parsing, execution, and scheduler delays, and **cannot be attributed to one of those factors without separate evidence**. The phase durations **combine JavaScript work, scheduling, and awaited network time**. They do not claim to identify server-only RPC execution time or data transfer latency. No account names, user/workspace IDs, token, URL, RPC payload, response, document content, or resource identifier enters the timing record. Unauthenticated results are discarded; identity/workspace changes, logout and revocation clear the in-memory snapshot.
- The existing **explicit five-second user-initiated profiler** adds a Long Tasks API observer only while sampling. Only numeric durations for observed main-thread tasks >=50 ms are aggregated, capped at 128 samples. It records **count, sum, maximum**, and a support flag. It never accesses attribution, task names, stack traces, user interactions, navigation URLs, network requests, or document contents. It disconnects immediately on sample completion, hidden tab, session/workspace interruption, or the bounded timeout. No continuous observer, network posting, storage, recording, or background agent.
- In **Account Settings → On-demand browser performance**, the report distinguishes page-navigation TTFB/DOMContentLoaded/load, post-module signed startup sub-phases, P50/P95 frame intervals and 60/120 FPS budgets, and optional Long Tasks data. It explicitly labels unavailable signed-startup and unsupported observer data instead of inventing measurements. The browser may not support the Long Tasks API; zero is meaningful only when supported.

## Automated verification

- Unit tests cover signed vs unauthorized phase retention, strict fixed phase labels, clock failure, decimal summaries, observer lifetime, observer disconnect, data minimization, and existing 5B compatibility.
- Real disposable-profile Chromium test checks the 1-second visible RAF sample, fixed-phase timeline, optional observer summary, and absent URL and user identifiers. The fixture serves only invented values on loopback.
- Full frontend validation, the established Priority 1–5B regression suites, the new on-demand-profile CI, and deployed-source SHA-256 checks are release gates.

## Acceptance and next evidence

The feature provides **diagnostic capability**, not a verified production performance improvement. Live signed-frame/long-task and startup-phase numbers must be generated by a user clicking **Measure 5 seconds** while signed in. Startup phase data requires a full reload with a valid signed session in the same tab, then an explicit sample. Do not add production write fixtures, credentials, monitoring services, or more caches to collect metrics. Follow-up optimization is justified only if the obtained durations reproducibly point to a specific phase or main-thread long task bottleneck.
