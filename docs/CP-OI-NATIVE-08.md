## Functional implementation
Generated confirmations are retained as exact bytes with a server-computed SHA256, byte count, filename, record identity, source revision, actor/time and linked generation audit. Upload client PO, externally generated confirmation or supporting file to native or historical order; PDF/PNG/JPEG up to 5 MiB. Content signature/type/size checks are not full malware scanning. Same-request retries use stable receipt IDs; changed payload conflicts; failed document insertion rolls back new generation receipt. Closing and reopening loses the in-memory retry ID; inspect history before attempting a new request. New document rows are append-only with existing workspace/module access; no separate role requirement. Original financial and historical payloads unchanged.

Workspace document registry and per-order document history use 25-row metadata pages; file bytes read only on demand. Display source PO, category, revision, creator UUID, timestamp, hash and byte count. Image thumbnails on demand; PDF download rather than inline PDF rendering. Browser verifies retrieved bytes against metadata SHA256 before download/thumbnail. Earlier CP07 audit-only receipts remain visible as unavailable bytes; source file/confirmation references displayed separately, not imported or counted as stored. Coverage counts all visible orders including archived, distinct orders with files/client PO/confirmation, actual file bytes/count, historical references and audit-only receipts. No proof of external delivery, signature authenticity or download-event logging implied. Large-file workload beyond the 5 MiB limit or production-scale storage performance has not been certified; object storage can be evaluated if needed. Existing business mutation/authorization semantics preserved.
